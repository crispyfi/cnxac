# Working in this config repo

This repo holds HPE Aruba Networking Central (new Central) AP and Central NAC configuration as plain API JSON, deployed with cnx-as-code (the `cnxac` command). Each folder is one Central environment. Its `env.yaml` names which.

## Rules

- **Run `cnxac check` after every change, and `cnxac plan` when you can.** `cnxac asbuilt` regenerates the as-built appendix, offline. Never run `cnxac apply`, `cnxac destroy` or `cnxac mpsk add`; a person does that.
- **Never add secret values:** PSKs, MPSK passphrases, shared secrets, passwords. They're set in the UI or generated by Central. Leave out fields such as `personal-security.wpa-passphrase`, `shared-secret-config` and `password`, and never add a `Password` column to `mpsk/`.
- **Never change an existing ID:** a NAC object's ID or any nested ID inside it. New objects and new rules leave their IDs empty (see below).
- **Never rename an MPSK WLAN.** Its auth profile can't follow, so the WLAN and every registered device would have to start again.
- **Never read or commit `credentials.yaml` or anything under `backups/`.**
- **Keep files as the API takes them:** plain JSON, no comments, no templating. When unsure of a body's shape, copy an existing file of the same type, or build the object in the UI in a lab and bring it in with `cnxac pull --add <type>`.
- **The file name is the object's name** (the SSID for a WLAN), with unsafe characters percent-encoded. The name inside the file is what counts.

## Layout

```
<folder>/
  env.yaml                       environment, protected flag, ignore list, Entra group names
  assign.yaml                    what's assigned at Global and at each site
  sites.yaml                     only where the tool creates the sites
  profiles/<type>/<name>.json    AP library profiles
  profiles/policy-groups.json    the policy order
  nac/<type>/<name>.json         Central NAC objects: auth-profiles, authz-policies
  nac/identity-management.json   written by pull for the as-built; never edit it
  mpsk/<WLAN>.csv                named MPSK entries: Name,Role,Enabled (Central's import format)
```

An object is managed only while it has a file. Deleting a file leaves the object in Central as it is; it doesn't delete it.

## Where site differences go

| A site needs… | Do this |
|---|---|
| a different radio, AP system, IDS, ARC, NTP, system administration or certificate usage profile | add the profile's file and list it under the site in `assign.yaml`; it replaces Global's there |
| its own value for an alias (Auth Server Address type only), e.g. its RADIUS accounting server | add the value under the site's `alias-values` in `assign.yaml`; the alias itself is listed under `global:` |
| a different WLAN setting | not possible: every site gets the same WLAN settings |

A site takes one profile of each of those types, so never list two of one type at the same site.

## How to

**Add a named VLAN.** Add `profiles/named-vlan/<name>.json` and list it under `global:` in `assign.yaml`. A WLAN that gives VLAN numbers in `vlan-id-range` needs nothing more: the tool doesn't manage layer 2 VLANs, which APs don't need.

**Add a role.** Add `profiles/roles/<name>.json`, listing its policies under `policies`. List the role under `global:` in `assign.yaml`. A new policy also needs its own file in `profiles/policies/`, an entry in `profiles/policy-groups.json` with a position no other entry has, and a line in `assign.yaml`.

**Add a WLAN.** Add `profiles/wlan-ssids/<ssid>.json` and list it under `global:` in `assign.yaml`.
- A Central NAC WLAN sets `cloud-auth: true` and must be in an auth profile's `networks` in `nac/auth-profiles/`. A new enterprise one must not set `primary-auth-server`.
- An MPSK WLAN gets its own MPSK auth profile, listing only that WLAN.
- An EAP auth profile uses the default server certificate (`eap.use-custom-server: false`); `check` refuses a custom one.
- A PSK WLAN is created disabled until someone sets its PSK in the UI.

**Add a device to an MPSK WLAN.** Add a row to `mpsk/<WLAN>.csv`: a name, a role that has its own file, and `TRUE` or `FALSE` for enabled. A person runs `cnxac mpsk add`, and Central generates the passphrase. Changing or removing a row changes nothing in Central; that's done in the UI.

**Add an authorization rule.** Edit the policy in `nac/authz-policies/`:
- Leave the IDs of the new rule and of each new condition, condition group and enforcement profile empty (`rule-id`, `condition-id`, `condition-group-id`, `profile-id`), and give each new enforcement profile a new `profile-name`.
- Rule positions must be unique within the policy, and policy positions unique across policies. Gaps are fine.
- An Entra group condition looks like `{"attr": "Authorization:<identity store ID>:GroupIds", "operator": "OP_CONTAINS_ELEM", "value": "<Entra group ID>"}`. Group IDs come from Entra; there's no lookup by name. Add the ID and the group's name under `group_names` in `env.yaml`, so the as-built shows the name.
- The role a rule gives is an `ATTR_ARUBA_ROLE` enforcement attribute, and the role needs its own file.

**Make the AP uplink check the RADIUS server's certificate** (802.1X on the uplink, `uplink-dot1xsupp`).
1. A person uploads the CA certificate that signed the RADIUS servers' certificate in the UI.
2. Add `profiles/certificate-usage/<name>.json` listing it for `AP1X`, and list it under `global:` in `assign.yaml`. This is the body the UI makes; keep its captive portal entry:
   ```json
   {"name": "<name>", "radsec-use-est-certificate": false, "cert-usage-assignment": [
     {"app-type": "CAPTIVE_PORTAL", "cert-name": "aruba_default", "cert-type": "SERVER_CERT", "sequence-id": 1},
     {"app-type": "AP1X", "cert-name": "<CA certificate name>", "cert-type": "CA_CERT", "sequence-id": 3}]}
   ```
3. Set `validate-server-cert` to `true` under the uplink profile's `uplink-dot1xsupp`.

`plan` reports a certificate name the environment doesn't have.

**New NAC IDs are left empty** (`""`): a new object's `auth-profile-id` or `policy-id`, and the nested IDs of a new rule. `apply` chooses each one and writes it into the file, which a person then commits. Never copy an ID from another object.

## Copying a folder to another environment

1. Copy the folder, leaving out `backups/`, `nac/identity-management.json` and any as-built, which describe the source, and change `environment:` in `env.yaml`. Set `protected: true` for production.
2. Delete `sites.yaml` if the sites already exist there.
3. Rename anything named differently in the target, such as ESSIDs or a profile prefix: the file name, the name inside it and every reference to it, including `assign.yaml`, the policy order, auth profiles' `networks` and `mpsk/` file names. Do this before the first apply, since an MPSK WLAN can't be renamed later.
4. Empty every NAC object's own IDs in `nac/`: `auth-profile-id`, `policy-id`, and each policy's `rule-id`, `condition-id`, `condition-group-id` and enforcement `profile-id`. Replace the identity store IDs in `nac/` with the target's. `cnxac ids` lists the target's stores and marks the IDs the folder uses that it lacks. Change certificate names too if the target's were uploaded under others; `cnxac ids` lists those as well.
5. Replace the Entra group IDs in authorization conditions if the target uses a different tenant, and their names under `group_names` in `env.yaml`. Nothing can check these, so check each one by hand.
6. Set each auth profile's `organization-name`, and replace the device lists in `mpsk/`.
7. Run `cnxac check` and `cnxac plan` against the new environment. A person creates the management users in the UI first, then runs `apply` and `mpsk add`. A `cnxac pull` afterwards writes the target's `nac/identity-management.json`.
